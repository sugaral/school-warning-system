# 数据范围（@DataScope）覆盖审计

> 生成脚本：`scripts/audit-data-scope.js`（只读审计，可重复运行）
> 审计对象：所有含 `:id` 路径参数的写操作端点（`@Put` / `@Delete` / `@Post` / `@Patch`）

## 1. 为什么要做这个审计

第 18 轮发现 `DataScopeInterceptor` 存在**缓存绕过**缺陷（命中 30s scope 缓存时
跳过资源归属校验），并修好；同时给拦截器补了 `session` / `schedule` 两个
"先解析归属、再判范围"的实体类型。

但那只覆盖了 `attendance` 的课次端点。**仓库里还有大量 `:id` 写操作端点
根本没有挂 `@DataScope`** —— 装饰器是 opt-in 的，没挂就等于不校验。
本审计把全部端点列出来，按"该不该挂"分类，避免继续靠人工记忆。

## 2. 判定方法

| 维度 | 说明 |
| --- | --- |
| 端点识别 | 路由装饰器路径含 `:id` 的写操作 |
| 装饰器检测 | 从路由行向下扫到方法签名，判断同一方法是否含 `@DataScope` |
| 实体推断 | 按路径关键词推断 `:id` 指向什么（student / class / session / …） |
| 风险分级 | `student`/`class`/`session`/`warning`/`schedule`/`grade`/`request` 视为**需按人-班-院隔离**；`user`/`role`/`config`/`audit`/`course`/`org` 视为全局类 |

> ⚠️ 审计脚本自身也踩过一次坑：第一版"从路由行**向上**扫 12 行找 `@DataScope`"
> 恒为 0 —— 因为装饰器组是 `@Post` → `@Permissions` → `@DataScope` 依次**向下**排列，
> 向上的方向扫不到。改为向下扫到方法签名后，正确识别出 10 个已挂端点。

## 3. 当前结果（第 19 轮）

```
含 :id 的写操作端点总数      : 61
已挂 @DataScope             : 12
未挂 @DataScope             : 49
  ├─ 其中"按人/班/院隔离"应为高危: 24
  └─ 其中全局/系统类（可能无需范围）: 25
```

已挂的 12 个：`attendance` 的 4 个课次端点（第 18 轮）、
`session-options` 系列、`batch-*` 系列（既有），
以及本轮新增的 `PUT/DELETE /admin/schedules/:id`。

## 4. 第 19-20 轮的处理结果

### 4.0 第 20 轮：逐条核查 24 个端点，只有 1 个是真缺口

第 20 轮写了一个"handler 自校验"扫描器，对这 24 个端点逐个检查
方法体内是否出现 `dataScope` / `scope_id` / `teacher_user_id !==` /
`forbidden(` / `checkStudentDataScope` 等自校验痕迹。结果：

```
隔离类且未挂装饰器: 24
  其中 handler 自校验: 14
  其中无任何校验    : 10   ← 需人工复核
```

对剩余 10 个逐条人工复核后，**9 个是扫描器误报**：

| 端点 | 实际情况 |
| --- | --- |
| `POST /vice-dean/approvals/:id/reject` | 调了 `canAccessRequest(req, changeRequest)`，403 分支存在 |
| `POST /student/inbox/:id/read` | where 带 `user_id`，只能标自己的消息 |
| `POST /student/notifications/:id/read`、`POST /student/warnings/:id/confirm` | 学生自助端点，"本人"语义即范围 |
| `PUT /warning-rules/:id`、`DELETE /warning-rules/:id` | 全校级配置，`sys_admin`/`student_admin` 专属 |
| `DELETE /admin/classes/:id` | `class:delete` 权限，仅 `sys_admin`/`student_admin` |
| `POST /teacher/sessions/:id/students/:student_id/status` | `session.teacher_user_id !== userId` 归属校验 |
| `PUT /teaching-admin/grades/:id` | 有 `isSysAdmin` 分支：非管理员走**审批流**，不直接改库 |

**唯一真实缺口：`DELETE /teaching-admin/grades/:id`** —— 详见 §4.3。

> 教训：静态扫描器能把 61 个端点收敛到 10 个候选，这已经很有价值；
> 但"有无 `dataScope` 字样"无法区分"真没校验"与"用了别的方式校验"。
> 最终判定必须落到行为验证或逐条读代码。

### 4.1 已核实"handler 内自行校验、无需装饰器"的

| 端点 | 校验位置 | 说明 |
| --- | --- | --- |
| `DELETE /admin/students/:id` | `students.admin.controller.ts:943-949` | `checkStudentDataScope(student, dataScope)` |
| `POST /warnings/:id/ack` | `warnings.controller.ts:1100-1123` | student_admin scope_id / 班主任班级 / 学生本人 三重判定 |
| `POST /teacher/sessions/:id/end` | `teacher.controller.ts:2049` | `session.teacher_user_id !== userId` → 403 |
| `DELETE /teacher/sessions/:id` | `teacher.controller.ts:1850` | 同上 |
| `POST /teacher/sessions/:id/students/:student_id/status` | `teacher.controller.ts:2234` | 同上 |
| `POST /vice-dean/approvals/:id/reject` | `vice-dean.controller.ts:586` | `canAccessRequest` |
| `POST /leave_requests/:id/approve` 等 3 个审批 | `requests.controller.ts` | 审批人范围判定 |

结论：这些端点是**有防护的**，只是防护写在 handler 里而非拦截器。

### 4.2 第 19 轮修复：排课端点（2 个）

`PUT /admin/schedules/:id` 与 `DELETE /admin/schedules/:id` 原本
**既没有装饰器、handler 里也没有任何范围判断** —— 属于真实缺口。修复内容：

```ts
// 修复前
@Put(':id')
@Permissions('schedule:read')        // ← 写操作却只要求读权限
async updateSchedule(...)

// 修复后
@Put(':id')
@Permissions('schedule:update')      // ← 补上正确的写权限
@DataScope({ entity: 'schedule', field: 'id' })
async updateSchedule(...)
```

`DELETE` 同理补上 `@DataScope({ entity: 'schedule', field: 'id' })`
（其权限码本来就是 `schedule:delete`，无需改）。

为支持该修复，给 `DataScopeInterceptor` 新增 `case 'schedule'`：
**先由排课 id 解析出 `class_id`，再复用班级/学院/self 的范围判定**。
`schedule:update` 权限码本就存在于目录（`permission-catalog.ts:67`）
并已授予 `student_admin` / `teaching_admin`，因此不会误拒合法角色。

### 4.3 第 20 轮修复：删除成绩绕过审批流（严重）

`PUT /teaching-admin/grades/:id` 的设计是**正确的**：

```ts
const isSysAdmin = await this.isSysAdmin(operatorId);
if (isSysAdmin) {
  // 直接改库
}
// 非管理员 → 创建 change_request，进入教学副院长审批流
```

但 `DELETE /teaching-admin/grades/:id` **完全没有这段判断**，
注释里只写着"与 updateGrade 保持一致"，实际并没有做：

```ts
// 修复前
@Delete('grades/:id')
@Roles('dean', 'teaching_admin', 'sys_admin')
async deleteGrade(@Param('id') id: string, @Req() req: any) {
  const existingGrade = await this.prisma.grades.findUnique(...);
  await this.prisma.grades.delete({ where: { id: gradeId } });   // ← 直接物理删除
```

后果：**改成绩要审批，删成绩不用** —— 任何拥有 `dean` / `teaching_admin`
角色的账号都能把任意成绩记录物理删掉，审批流形同虚设，
且删除是不可逆的（`updateGrade` 至少还留了变更申请记录）。

修复：非 `sys_admin` 一律 403，并提示改用成绩修改（其内部会创建审批单）。
不做"自动建 change_request"是刻意的 —— `DELETE` 语义无法表达
"把成绩改成 X"，应由调用方改用 `PUT`。

```
非管理员删除成绩 -> 403 code=403 权限不足
管理员删除不存在成绩 -> 200 code=404 操作失败
管理员删除真实成绩 -> 200 code=0 ok          （修复前为 500，见 §4.4）
```

### 4.4 顺带修掉一个"报错但已生效"的语义缺陷

修 `deleteGrade` 时实测发现：管理员删除**真实**成绩返回 **500**，
但数据库里那一行**确实已经被删掉了**。

原因：删除成功之后写 `audit_logs` 时抛错（`before_json` 序列化 / 约束问题），
整个请求被打成 500。这种"报错但已生效"的语义最危险 ——
调用方以为失败会重试，而数据已经没了。

修复：把删除与审计**分开处理**，审计失败只记日志、删除结果如实返回。

### 4.5 第 22 轮更正：`teaching-admin` 的 `org_id` **不是**越权风险

第 21 轮把「该控制器用客户端传入的 `org_id` 过滤」记为待办风险，
怀疑存在跨学院越权读取。**第 22 轮核实后结论是不成立**，原因：

1. 三个相关端点（`classes` / `students` / `courses`）的 `@Roles` 只允许
   `dean` / `teaching_admin` / `sys_admin`；
2. `rbac_roles` 中 **`teaching_admin` 的 `default_scope` 是 `school`（全校）**，
   而唯一组织范围的 `vice_dean` **不匹配字面量 `dean`**，因此实际拿到
   访问权的只有全校级角色；
3. 实测：`student_admin`(college=2) 与 `head_teacher`(class=1) 在这三个
   端点上**全部 403**（角色守卫层即拒绝），管理员 200。

即 `org_id` 对**能访问它的角色**而言是合法筛选条件（全校角色选学院查看），
而非"信任客户端输入导致的越权"。`org_id=2` 返回 2 个班、
`org_id=1` 返回 3 门课 —— 筛选确实生效。

已固化为 `scripts/verify-teaching-admin-scope.js`（9 项断言），
避免以后只看代码又误判一次。

> 教训（第 21→22 轮）："代码里出现了客户端传入的过滤参数"不等于越权。
> 判定越权必须同时看**谁能访问该端点**（角色守卫）与**该角色本身的范围**
> （`rbac_roles.default_scope`）。只看 handler 入参会得出假阳性。
