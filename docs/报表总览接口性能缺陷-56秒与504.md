# 报表总览接口性能缺陷 —— 56 秒 / 504 网关超时

## 1. 现象（实测）

通过前端 nginx 代理访问管理端「报表」页时接口超时：

```
FAIL 报表总览  HTTP 504
```

绕开 nginx 直连后端量真实耗时：

```
/admin/reports/overview        => HTTP 200  耗时 56310ms  响应 401 字节
/admin/reports/history?page=1  => HTTP 200  耗时 8ms      响应 2337 字节
```

**56 秒返回 401 字节** —— 典型的"算了海量数据、只用了几个数字"。

nginx 默认 `proxy_read_timeout` 是 **60 秒**，56s 距超时只差 3.7 秒。
也就是说：这份数据量下勉强能返回，数据再涨一点就必然 504。

## 2. 根因

`ReportsController.findWarningsForReport()`（`src/reports/reports.controller.ts`）
的 `where` 只按 `created_at` 过滤，**没有 `take`**：

```ts
return this.prisma.warnings.findMany({
  where,                       // 仅 created_at 区间 + 权限范围
  select: { /* 12 个字段，含 trigger_detail_json */ },
  orderBy: { created_at: 'desc' },
});                            // ← 没有 take，全量物化
```

放大因素：

| 因素 | 实测值 |
| --- | --- |
| `warnings` 表总行数 | 162,378 |
| 单次 overview 触发的窗口查询 | 4 个（day / week / month / term） |
| 每个窗口取回的行数 | 最多约 5 万行 |
| 每行含 `trigger_detail_json`（JSON 大字段） | 是 |
| `buildWarningContext()` 对 term 窗口全部行做学生查询 | 是（unique student_id 上万） |

即：每次请求要把 5 万+ 行完整对象从 MySQL 取回、经 Prisma 反序列化，
再在 Node 里建 Map。`created_at` 上其实**有**索引
（`warnings_created_at_status_idx`），但 `findMany` 仍然要取回所有匹配行。

同一个 `findWarningsForReport` 还被日报 / 周报 / 月报 / 学期报表
四个接口共用，所以**这一处未加限制，五个接口一起慢**。

## 3. 修法

### 3.1 明细查询加扫描上限

```ts
const REPORT_WARNING_SCAN_LIMIT = 5000;

return this.prisma.warnings.findMany({
  where, select: { ... },
  orderBy: { created_at: 'desc' },
  take: REPORT_WARNING_SCAN_LIMIT,   // ← 索引范围扫描 + LIMIT
});
```

### 3.2 汇总数字改走 `count()`

只加 `take` 会引入**更糟的问题**：用 `warnings.length` 当总数会顶到上限，
把截断伪装成业务数字（实测四个窗口全部变成 `5000`，而真实是 162,378）。

因此新增 `countWarningsForReport()`，汇总数字用 `COUNT(*)`：

- `COUNT(*)` 只走索引做范围扫描，**不需要取回行数据、不经 Prisma 反序列化**，
  比 `findMany` 便宜一到两个数量级（实测约占冷启动 1.9s 中的小头）；
- 返回值语义回到"区间内全部预警数"，与修复前一致。

明细/分布仍用带 `take` 的 `findWarningsForReport` —— 那才是真正贵的地方。

### 3.3 显式暴露采样上限

响应里新增 `summary.distributionSampleLimit`，让前端能提示
"分布基于最近 N 条"，避免把采样分布误读为全量分布。

## 4. 修复后实测

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| `/admin/reports/overview` 冷启动 | **56,310 ms** | **1,952 ms** |
| 同上（命中 60s dashboard_cache） | 56,310 ms | **7–10 ms** |
| 经 nginx 访问 | **HTTP 504** | HTTP 200 |
| 汇总数字准确性 | 正确但极慢 | **正确**（`count()`，162,378） |

约 **28 倍**提升，且计数语义未退化。

响应内容核对：

```json
summary        = {"todayWarnings":162378,"weeklyWarnings":162378,
                  "monthlyWarnings":162378,"semesterWarnings":162378,
                  "exportCount":10,"distributionSampleLimit":5000}
monthlyLevel   = {"red":1250,"orange":1250,"severe":1250,"yellow":1250,"other":0}
semesterOrgRank= [{"total":5000,"closed":0,"org_id":"2","org_name":"计算机学院","closeRate":0}]
recentExports  = 10 条
```

注意 `monthlyLevel` 四项之和 = 5000 = 采样上限，说明分布确实基于采样；
而 `summary` 的 162,378 是精确值。

## 5. 已知局限（诚实记录）

- **`semesterOrgRank` 的 `total` 现在是采样值**（5000），不是全学期总数。
  它是"最近 5000 条里的学院分布"。若要精确排行，需要改成
  `groupBy(['org_id'])` 聚合（另一次改动）。
- **`monthlyLevelStats` 同理**，是最近 5000 条的等级分布。
- 当前测试数据里四个时间窗的数字恰好相同（162,378），因为 16 万条预警
  全部落在同一学期且集中在最近几天。这是**数据分布特性**，不是统计错误；
  用真实历史数据时四个窗口应有差异。
