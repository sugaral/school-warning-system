# 签到课次接口缺陷 —— 入参不校验 + 数据范围未生效

> 对应任务书 §6.0.x 中「`POST /attendance/sessions` 传 ISO datetime 返回 500」
> 这一条。实测结论：**原始症状已不复现，但同一段代码里藏着两个更严重的问题**。

## 1. 原始症状复核

任务书记录「ISO datetime 返回 500」。本轮用 8 种 `start_time` 传法逐一对拍：

| 传法 | 结果 |
| --- | --- |
| `2026-09-12T10:00:00.000Z` | ✅ code=0 |
| `2026-09-12T10:00:00+08:00` | ✅ code=0 |
| `2026-09-12T10:00:00` | ✅ code=0 |
| `2026-09-12 10:00:00` | ✅ code=0 |
| `2026-09-12` | ✅ code=0 |
| `not-a-date` | ❌ **code=500** |
| ``（空串） | ❌ **code=500** |
| `1789000000000`（时间戳） | ❌ **code=500** |

**结论：ISO 时区格式本身没问题**（`new Date()` 能正确解析），
真正 500 的是**非日期输入**。所以任务书那句描述的症状定位不准，
但"这个接口会 500"是对的。

## 2. 缺陷 1：`start_time` 完全不校验

修复前的代码：

```ts
const start = new Date(dto.start_time);   // ← 无任何校验
```

`new Date('not-a-date')` 得到 Invalid Date，`getTime()` 为 `NaN`，
NaN 一路传进 Prisma：

```
Invalid `prisma.schedules.findMany()` invocation:
  session_start: { gte: Invalid Date, lt: Invalid Date }
```

更糟的是控制器自己的 catch 把它转成 `{code:500}` 并作为
**HTTP 201** 返回 —— 客户端按状态码判断会以为**创建成功**。

### 修复

新增 `shared/date-time.util.ts`：

- `parseDateTimeInput(value, field)` —— 正则白名单 + Date 有效性双重校验，
  只接受 ISO（带/不带时区）、`YYYY-MM-DD HH:mm:ss`、`YYYY-MM-DD`；
  对纯数字时间戳给出**针对性**提示而不是笼统的"格式错误"；
- `isValidSessionStart(date)` —— 业务边界，允许 ±1 年（覆盖补录与提前排课），
  挡掉 1970 / 9999 这类会让签到窗口与迟到判定全部失真的脏输入。

**实测（修复后）**：

```
start_time=非法字符串  → code=400  start_time 格式不正确（收到 "not-a-date"），支持 ISO 8601…
start_time=空         → code=400  start_time 不能为空
start_time=时间戳      → code=400  start_time 不接受纯数字时间戳（收到 "1789000000000"）…
start_time=越界 1970   → code=400  课次开始时间过早（1970-01-01T00:00:00.000Z），不应早于一年前
```

同时把 catch 改为 `throw new InternalServerErrorException(...)`，
交给全局 `HttpExceptionFilter`，使 **HTTP 状态码与响应体一致**
（此前是 HTTP 201 + `code:500`）。

> 关于 `HTTP 201 + code:400`：本仓库有 **320 处**控制器内手写业务错误码，
> 前端统一读 `response.data.code === 0` 判断成功（`api/http.ts` 的
> 成功分支不抛错，组件自己看 `code`）。为保持一致，校验失败仍用
> `code:400`；只有**真实异常**才改为抛 HTTP 5xx。

## 3. 缺陷 2：数据范围校验缺失（越权写入）

`createSession` 是**唯一**没有 `@DataScope` 的 sessions 端点，
而 `batch-create` / `batch-end` / `batch-delete` / `batch-*-job` 都有：

```ts
@Post('sessions')                    // ← 唯独这个没有
@Permissions('attendance:manage')
```

后果：任何拥有 `attendance:manage` 的角色（含 `head_teacher`）都能给
**任意班级**开签到课次 —— 越权写入。

### 修复过程中的一次踩坑（值得记录）

第一版修法是直接补上 `@DataScope({ entity: 'class', field: 'class_id' })`，
结果 **张老师连自己班的课次都建不了**（code=403「权限不足，无法访问此资源」）。

根因在 `DataScopeInterceptor.collectScopedResourceChecks`：它会把 body 里的
`course_id` 也当作 `course` 实体做范围校验，而其 `case 'course'` 只处理
college / self：

```ts
case 'course': {
  ...
  if (dataScope.type === 'college' && dataScope.collegeIds) { ... }
  break;                 // ← class 范围直接落空 → return false → 403
}
```

`batch-create` 等端点虽然挂了同一个装饰器，却因为**不带 course_id**
而侥幸绕开了这个分支。

### 最终修法

移除该端点的 `@DataScope`，改为在 handler 内做**显式**范围判定
`assertCanManageClass()`：

| scope | 判据 |
| --- | --- |
| all | 放行 |
| college | 班级 `org_id` 在范围内 |
| class / self | 班级 id 在范围内；**教师额外允许授课绑定的班级** |
| 其它 | 拒绝 |

其中"授课绑定"通过 `course_classes` / `schedules` 判教师是否给该班上课
（`isTeacherOfClass`），这样非班主任但确实授课的教师也能开课次。

### 实测（修复后）

```
[1] 张老师(head_teacher, class=1) 给本班(class=1) 开课次: code=0   ✅ 允许
[2] 张老师给外班(class=2) 开课次:                      code=403 ✅ 已拒绝
```

数据核对：`course_classes` 中张老师(user=2) 绑定的是 course 1/2 → class 1；
李老师(user=3) 绑定 course 1 → class 2。因此上表结论与绑定关系一致。

## 4. 第 18 轮更正：`request.dataScope` **是**被填充的

> ⚠️ 本节替换第 17 轮的错误结论。上一轮写"`req.dataScope` 恒为 undefined、
> `@DataScope` 形同虚设"，**这是错的**，原因见下。

### 4.1 错误结论是怎么产生的

第 17 轮的调试日志只打在 `createSession` 一处，而那正是**唯一没有**
`@DataScope` 的 sessions 端点 —— 它当然拿不到 scope。用单个端点的观测
去推断全局机制，是这次的判断错误。

第 18 轮改用**行为对照**（同一端点下不同 scope 角色返回的数据量）：

| 端点 | 管理员(all) | 班主任(class 1) | 教师(class 2) | 结论 |
| --- | --- | --- | --- | --- |
| `GET /admin/classes` | 2 | **1** | 403 | ✅ scope 生效 |
| `GET /admin/students/export-accounts` | 10005 | 403 | 403 | ✅ |
| `GET /admin/course-classes` | 4 | 403 | 403 | ✅ |
| `GET /admin/warnings/student` | 0 | 0 | 403 | ✅（业务数据为空，无对照价值） |

班主任拿到 1 个班、管理员拿到 2 个班 —— **scope 确实在起作用**。
`DataScopeInterceptor` 对带 `@DataScope` 的端点会正常写入 `request.dataScope`
并做资源归属校验。

### 4.2 真正的问题在别处：**缓存命中时跳过校验** 🔴

第 18 轮定位到一个**严重且此前未发现**的缺陷。
`DataScopeInterceptor.intercept` 有三条提前返回路径，
其中"命中 30 秒 scope 缓存"这条**直接放行，不做资源校验**：

```ts
const cachedDataScope = await this.getCachedValue(...);
if (cachedDataScope) {
  request.dataScope = cachedDataScope;
  return next.handle();          // ← 跳过了 assertScopedResourceAccess
}
```

后果：**同一次会话里，第一个请求校验资源归属，之后的全部跳过。**
即"越权只需先用任意合法请求预热缓存"。

实测证据（修复前，张老师 scope=class 1，目标均为 class 2 的课次）：

| 顺序 | 请求 | 结果 |
| --- | --- | --- |
| 1 | `DELETE /attendance/sessions/{class2}` | 403（首个请求，确实校验了） |
| 2 | `POST /attendance/sessions/{同一课次}/end` | **201 成功** |
| 3 | `POST .../status` | **201 成功** |

调试日志直接印证：

```
[DSY] DELETE /attendance/sessions/35 ... scopeType=class classIds=["1"]
[DSZ] POST /attendance/sessions/35/end    命中缓存，跳过校验 scopeType=class
[DSZ] POST /attendance/sessions/35/status 命中缓存，跳过校验 scopeType=class
```

**修复**：把资源校验抽成 `assertScopedResourceAccess()`，
让**四条**路径（命中缓存 / 无角色 / 系统范围 / 正常计算）全部经过它。

### 4.3 第二个问题：`entity: 'class'` 对课次路由是错的

修复过程中发现，给 `POST /attendance/sessions/:id/end` 挂
`@DataScope({ entity: 'class' })` 会**把功能改死**：本路由的 `:id` 是
**课次 id**，而拦截器对 `entity='class'` 的处理是把它当**班级 id** 查：

```ts
this.prisma.classes.findUnique({ where: { id: Number(:id) } })
```

调试证据：

```
[DSC] entity=class resourceId=42 scopeType=class classIds=["1"]
[DSC-class] id=42 found=false class_id=n/a     ← 课次 id 在 classes 表查不到
```

于是**连自己班的课次也被 403**。实测确认（修复前）：

```
DELETE 张老师(scope=class1) → class=1 课次(46): HTTP 403
DELETE 张老师(scope=class1) → class=2 课次(47): HTTP 403   ← 两个都拒，是假安全
```

**修复**：给拦截器补 `case 'session'` —— 先用课次 id 解析出 `class_id`，
再复用班级/学院/self 的范围判定；四个端点改挂
`@DataScope({ entity: 'session', field: 'id' })`。

### 4.4 修复后实测（`scripts/verify-session-mutation-scope.js`）

```
--- A. 张老师(scope=class 1) 操作 class=2 课次（应全部拒绝）---
  OK   DELETE sessions/:id          HTTP 403
  OK   POST sessions/:id/end        HTTP 403
  OK   POST sessions/:id/status     HTTP 403
--- B. 张老师(scope=class 1) 操作 class=1 课次（应允许，防止改死）---
  OK   POST sessions/:id/status     HTTP 201 code=0
  OK   POST sessions/:id/end        HTTP 201 code=0
--- C. 系统管理员（scope=all，应不受限）---
  OK   POST sessions/:id/status     HTTP 201 code=0
--- D. 越权删除不得真的删掉数据 ---
  OK   课次在越权删除后仍存在  前 17 → 后 17

=== 结果：7 通过 / 0 失败 ===
```

> 注：这些 POST 端点成功时返回 **HTTP 201 + code:0**（Nest 对 POST 的默认
> 状态码）。第 18 轮第一版断言写死了 `status === 200`，导致 B/C 段误报失败；
> 断言已改为接受 2xx。

## 5. 仍未闭环

- **其它带 `:id` 但实体类型声明不当的路由**：本轮只核实并修好了
  `attendance` 的 4 个课次端点。仓库中另有约 50 个 `:id` 写操作端点
  未挂 `@DataScope`（见 `docs/13-全量自测报告.md` 的审计输出），
  其中哪些需要、哪些不需要，需按业务逐条判断。
- **`case 'course'` 仍不处理 class 范围**：`checkResourceByEntity` 的
  course 分支只支持 college/self。未受影响是因为本轮避开了它；
  若将来有"按 course_id 判范围"的路由，会再次踩坑。
- **`@DataScope` 缺失的端点默认放行**：这是既有设计（装饰器是 opt-in），
  不是本轮引入的，但对越权防护是系统性风险。
