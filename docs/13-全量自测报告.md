### 2.1 数据范围收敛（关键结论）

| 角色 | scope | `stats/summary.totalStudents` |
| --- | --- | --- |
| 系统管理员 | 全局 | **10005** |
| 王学工 student_admin | college(2) | 10005（本学院 = 全校，本环境只有 1 个学院） |
| 张老师 head_teacher | class(1) | **5003**（本班人数，与 `class_id=1` 实际人数一致） |
| 李老师 teacher | class(2) | 访问 `/admin/students` → **403** |

判据：`head_teacher` 的 5003 **严格小于**全局 10005，证明 scope 真实生效
（若相等则说明 scope 未生效，那才是缺陷）。

### 2.2 一个容易误判的点

不是越权。这类端点的正确判据是**数据范围收敛**，而非 403。
第一版自测脚本把它们当越权，一次性报出 8 个假失败 —— 已修正。

## 3. 并发自测

并发 20、5 轮。

| 场景 | 请求 | 2xx | 5xx | 超时 | P50 | P95 | P99 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A 混合只读（5 接口） | 100 | 100 | 0 | 0 | 75ms | 220ms | 224ms |
| B 并发创建导出任务 | 10 | 10 | 0 | 0 | 39ms | 42ms | 42ms |
| C1 并发读站内消息 | 20 | 20 | 0 | 0 | 44ms | 48ms | 48ms |
| C2 并发标记同一条已读 | 10 | 1 | 0 | 0 | 18ms | 18ms | 18ms |
| D 并发登录（bcrypt） | 20 | 20 | 0 | 0 | 142ms | 185ms | 185ms |

### 3.1 结论

- **无 5xx、无超时、无重复副作用**
- B：10 并发生成的导出任务 ID **去重后仍为 10** → 无重复写入
- C2：**恰好 1 次成功 + 9 次 404** → 严格的幂等语义（见 §3.2）
- D：P95 = 185ms。历史故障是 bcryptjs 阻塞事件循环导致 **P99 2929ms**，
  换用 `@node-rs/bcrypt`（Rust）后回到百毫秒级。

### 3.2 并发自测发现的真实缺陷：`markRead` 不幂等

原始实现：

```ts
await prisma.notification.updateMany({
  where: { id, user_id },          // ← 没有 status 条件
  data: { status: 'read' },
});
return result.count > 0;
```

并发 10 次调用同一条消息，**10 次全部返回成功** —— 因为 Prisma 把
"把 read 再写成 read" 也算作命中（count=1）。后果：
接口语义变成"每次调用都声称刚刚标记成功"，前端无法区分
"此次真的从未读变已读" 与 "本来就已经读过"。

修复：where 增加 `status: 'unread'`，只有**真实状态迁移**才返回 true。

修复后实测：`成功 1 / 404 9`。

> ⚠️ 第一版该用例选了一条**已经是已读**的消息，于是 10/10 返回 404，
> 看起来"没有 5xx 就算通过"，实际上没有真正验证迁移语义。
> 现在脚本会先插入一条确定的未读探针，保证起点可复现。

## 7. 第 18 轮：数据范围校验的严重缺陷（已修）

第 17 轮曾误判「`request.dataScope` 未被填充、`@DataScope` 形同虚设」。
**该结论是错的** —— 当时只在 `createSession`（唯一无装饰器的端点）打日志，
属于用单点观测推断全局。第 18 轮用行为对照证明 scope 正常工作：
班主任看到 1 个班、管理员看到 2 个班。

真正的问题在别处：

### 7.1 缓存命中时跳过资源校验（严重）

`DataScopeInterceptor` 的"命中 30 秒 scope 缓存"分支直接 `return next.handle()`，
**不做资源归属校验**。于是同会话中首个请求校验、其余全部放行：

| 顺序 | 请求（张老师 scope=class 1 → class 2 的课次） | 修复前 | 修复后 |
| --- | --- | --- | --- |
| 1 | `DELETE /attendance/sessions/{id}` | 403 | 403 |
| 2 | `POST .../{id}/end` | **201 成功** | 403 |
| 3 | `POST .../{id}/status` | **201 成功** | 403 |

已把校验抽为 `assertScopedResourceAccess()`，四条路径全部经过。

### 7.2 `entity: 'class'` 用在课次路由上会把功能改死

课次路由的 `:id` 是**课次 id**，而 `entity='class'` 会拿它去查 `classes` 表，
必然 not found → 连自己班也 403（假安全）。已为拦截器补 `case 'session'`
（课次 → class_id → 范围判定），4 个课次端点改挂
`@DataScope({ entity: 'session', field: 'id' })`。

### 7.3 修复后实测

```
A. 外班 DELETE / end / status  → 全部 403
B. 本班 status / end           → 全部 201 code=0（未改死）
C. 管理员 status               → 201 code=0
D. 越权删除后课次仍存在         → 前 17 → 后 17
=== 7 通过 / 0 失败 ===
```

脚本：`scripts/verify-session-mutation-scope.js`、`scripts/verify-data-scope.js`。

### 7.4 仍未闭环

- 仓库中约 **50 个** `:id` 写操作端点未挂 `@DataScope`，哪些该挂需逐条按业务判断；
- `checkResourceByEntity` 的 `case 'course'` 仍不处理 class 范围；
- `@DataScope` 是 opt-in，未挂的端点默认放行（既有设计，非本轮引入）。
